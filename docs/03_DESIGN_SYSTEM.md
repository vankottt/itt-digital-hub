# CIT WEBSITE — DESIGN SYSTEM DIRECTION

## Visual north star
Stanford Institute for Human-Centered AI (HAI) is the primary visual benchmark.
This does NOT authorize cloning Stanford layouts, branding, colors, logos or proprietary visual assets.

## Desired visual character
- Institutional confidence.
- Editorial clarity.
- Contemporary research organization.
- Human, serious and calm.
- Generous whitespace.
- Strong typography hierarchy.
- Large, purposeful imagery.
- Minimal decorative UI.
- Technology is visible through systems, data and diagrams rather than AI clichés.

## CIT differentiation
CIT must feel more engineered and systems-oriented than HAI. Add a distinctive visual layer based on:
- system maps;
- process flows;
- layered architectures;
- actor/relationship networks;
- feedback loops;
- structured metadata;
- data visualisation;
- subtle grid/diagram logic.
These elements must explain methodology or evidence. They must not be ornamental pseudo-technical graphics.

## Visual grammar rule
HAI defines the visual grammar.
Other benchmarks define content/function patterns.
A Turing-style project structure, CSH-style visualisation or Dark Matter-style system diagram must still be rendered in one coherent CIT visual language.

## Base composition
Prefer:
- light / white-dominant pages;
- dark graphite text;
- one deep institutional tone such as navy/deep teal;
- one distinctive CIT accent color;
- occasional dark sections only where data/methodology visualization benefits.
Exact brand colors are NOT frozen until visual concepts are approved.

## Typography direction
Primary: modern editorial sans-serif with strong readability and character.
Secondary/utility: restrained mono or technical sans only for metadata, diagrams and system labels.
Avoid a software-dashboard typography feel.
Do not use a mono font for large body copy.

## Layout
- Wide but disciplined content containers.
- Strong vertical rhythm.
- Large section spacing.
- Fewer, larger content moments rather than many small cards.
- Alternate editorial layouts to avoid repetitive left-text/right-card sections.
- Use full-bleed or wide media selectively.
- Keep the first viewport focused and calm.

## Hero
The hero should feel like a research institution, not a SaaS landing page.
Avoid:
- badges;
- pills;
- fake stats;
- dashboards;
- gradient-glow AI art;
- multiple competing CTAs.
Use one strong proposition, concise support copy and restrained action hierarchy.

## Imagery
Preferred:
- authentic researchers/people when available;
- architecture/infrastructure/context photography when relevant;
- real project imagery;
- original system diagrams and data visuals.
Avoid generic stock handshakes, glowing brains, robots, circuit-board faces and generic blue technology overlays.

## System-diagram language
Use diagrams as a signature CIT asset family.
Recommended characteristics:
- clear nodes and relationships;
- labels that read as real information;
- restrained lines and arrows;
- hierarchy through scale/weight rather than rainbow coloring;
- responsive simplification on mobile;
- motion only to explain sequence, state or feedback.

## Methodology visual
The site should be able to express a loop such as:
Understand / Define → Map → Analyse → Redesign → Implement → Measure → Adapt → repeat.
The exact naming is a website communication model until formally approved as official methodology language.

## Motion
Use purposeful motion only:
- diagram progression;
- subtle content reveal;
- state transitions;
- hover/focus feedback.
Respect prefers-reduced-motion.
No ambient animation merely to make the site feel technological.

## Buttons and controls
- Minimal variants.
- Clear primary/secondary hierarchy.
- No excessive rounded-pill treatment unless approved by visual concept.
- Accessible focus states.
- Consistent icon family and stroke logic.

## Cards
Cards are not the default container.
Prefer open editorial layouts, lists, media blocks and structured bands. Use cards only where a repeatable object genuinely needs containment, such as projects or insights.

## Responsive design
Do not design desktop first and merely stack everything on mobile.
For mobile:
- preserve the hierarchy of the hero;
- simplify diagrams without making them unreadable;
- reduce decorative density;
- retain generous but practical spacing;
- verify Bulgarian line lengths and wrapping independently from English.

## Accessibility
Target WCAG 2.2 AA behavior where practical:
- sufficient contrast;
- visible keyboard focus;
- semantic headings;
- meaningful alt text;
- accessible nav/menu behavior;
- reduced-motion support;
- diagrams accompanied by textual meaning.

## Anti-patterns
Never introduce without explicit approval:
- generic AI gradients;
- neon cyber aesthetics;
- glassmorphism as a theme;
- bento-grid filler;
- fake command-line labels;
- decorative data dashboards;
- dozens of icon cards;
- startup-style social proof metrics;
- imagery or copy that implies unconfirmed achievements.

## Design approval rule
Before full homepage implementation, create original CIT high-fidelity concepts for the major homepage sections and at least one mobile view. In autonomous Goal mode, evaluate the alternatives against this design contract, select the strongest coherent direction, record the decision, and treat it as the internal production design spec. Do not pause for routine aesthetic approval. In interactive design-review mode, explicit human approval may replace this internal selection step.

## LIVE VISUAL REFERENCE POLICY
Use live benchmark pages as on-demand visual evidence, not as source-of-truth specifications.

Primary Stanford HAI references:
- Homepage — https://hai.stanford.edu/
- About / institutional positioning — https://hai.stanford.edu/about
- Research — https://hai.stanford.edu/research
- Policy — https://hai.stanford.edu/policy

When inspecting HAI, study relationships such as typography hierarchy, whitespace, content width, media scale, navigation restraint, editorial rhythm and institutional tone. Do not measure/copy exact CSS values, page compositions, brand colors, typography implementation or proprietary assets.

Reference hierarchy:

1. Approved CIT source material and Build Pack
2. Selected original CIT design concept/system
3. Live benchmark pages as supporting evidence

If a benchmark changes later, it does not automatically change the CIT design. The selected original CIT design system remains authoritative until deliberately revised.
